**PRD ID:** PRD-LIC-001

## 1. Product Overview

### 1.1 Purpose
Add an offline-capable licensing system to Tuari that enforces edition-based feature gating, supports perpetual and subscription license models, and provides tamper resistance appropriate for a desktop ERP application.

### 1.2 Scope
- License file creation and validation
- Edition model (Standard, Professional, Enterprise)
- Feature gating in Rust shell and API sidecar
- License activation UI
- Grace period / trial mode
- Lost license recovery
- Offline activation via response file
- Clock tampering resistance
- License generation tooling (internal)

### 1.3 Out of Scope (v1)
- Operation-count-based trial limits (v2)
- Floating licenses / concurrent seat tracking (v2)
- Online subscription auto-renewal (v3)
- Usage analytics / telemetry (v2)

## 2. Features

### F1: License File Format & Validation
**Priority:** P0

**Description:** Define a signed license file format (`license.lic`) with Ed25519 cryptographic signatures. The file contains the edition, feature flags, validity dates, and customer metadata.

**Acceptance Criteria:**
- [ ] A `license.lic` file can be generated by an internal CLI tool.
- [ ] The file uses the format `<base64url(payload)>.<base64url(signature)>`.
- [ ] The payload is validatable JSON conforming to a defined Zod schema.
- [ ] The Ed25519 signature can be verified against a public key embedded in the Rust binary.
- [ ] Invalid, tampered, or malformed files are rejected with a clear error message.
- [ ] The file decodes to a `LicenseInfo` struct containing: `licenseId`, `edition`, `features[]`, `maxUsers`, `validFrom`, `validUntil`, `licenseType`, `customerName`, `customerEmail`.

### F2: Edition Model
**Priority:** P0

**Description:** Define three product editions — Standard, Professional, Enterprise — each with a distinct feature set.

**Acceptance Criteria:**
- [ ] Standard edition: all existing features, single user, local-only.
- [ ] Professional edition: adds LAN server mode, multi-user (up to 10 accounts), advanced reports, external API access.
- [ ] Enterprise edition: adds encrypted database (SQLCipher), unlimited users, multi-site sync, audit export, priority support.
- [ ] The license file contains the edition name and an explicit feature flags array that overrides edition defaults (additive only).
- [ ] Feature flags are validated against a known enum at license parse time.

### F3: Feature Gating — Rust-Enforced (Encrypted Database)
**Priority:** P0

**Description:** The Rust Tauri shell must prevent the encrypted database feature from being used without an Enterprise license.

**Acceptance Criteria:**
- [ ] If `APP_DB_KEY` is set in the environment but the license does not include the `encrypted_db` feature, the Rust shell strips the key from the sidecar's environment.
- [ ] The Rust shell uses `.env_clear()` before setting allowed environment variables, preventing system-level `APP_DB_KEY` from leaking.
- [ ] The sidecar crashes at startup if it cannot read the encrypted database (natural consequence — no separate error handling needed).

### F4: Feature Gating — API-Enforced (All Other Gated Features)
**Priority:** P0

**Description:** Business-logic feature gates in the Hono API sidecar must prevent unauthorized access to gated features.

**Acceptance Criteria:**
- [ ] An `app.use()` or per-route middleware reads license info from structured environment variables (`TUARI_LICENSE_EDITION`, `TUARI_LICENSE_FEATURES`, etc.) set by the Rust shell. The raw signed license payload is never exposed to the sidecar.
- [ ] If a feature is required but not licensed, the endpoint returns HTTP 402 with error code `UPGRADE_REQUIRED`.
- [ ] The response includes the minimum edition required for the feature.
- [ ] Gated features include: LAN server binding check, max users check on account creation, advanced report endpoints, audit export, external API access.
- [ ] A `requireFeature(feature: string)` middleware function exists and is composable with existing auth/permission middleware.

### F5: License Activation (File Upload)
**Priority:** P0

**Description:** Users can activate a license file by selecting it through the application UI.

**Acceptance Criteria:**
- [ ] A "Activate License" button exists in Settings → Licensing.
- [ ] Clicking it opens a native file picker dialog for `.lic` files.
- [ ] The file content is sent to a Tauri command `activate_license(content: string)`.
- [ ] The Rust shell validates the signature, parses the payload, checks dates, and writes the file to `<app_data>/Tuari/license.lic`.
- [ ] Success/failure is returned to the frontend with an Arabic message.
- [ ] On success, the license info is cached in memory; a restart is not required for feature changes unless stated (LAN server mode requires restart).

### F6: Grace Period & Trial Mode
**Priority:** P0

**Description:** Users can evaluate the application for 30 days without a license. After the grace period, non-licensed mode is locked.

**Acceptance Criteria:**
- [ ] On first launch, if no `install-timestamp` file exists, create it with the current time.
- [ ] If no license is present and the install is < 30 days old, the app starts with Standard edition features.
- [ ] A badge in the bottom-right corner shows "النسخة التجريبية — يتبقى N يوم".
- [ ] The Settings → Licensing page shows a countdown and upgrade CTA.
- [ ] If the install is > 30 days old with no license, the app shows a full-screen activation prompt and blocks business operations.
- [ ] Existing data remains on disk and is accessible after activation.

### F7: Three-Phase License Expiry
**Priority:** P1

**Description:** When a license has a `validUntil` date, the app provides three phases of behaviour as expiry approaches.

**Acceptance Criteria:**
- [ ] 30+ days before expiry: normal operation.
- [ ] 1-30 days before expiry: warning banner on every page "ينتهي الترخيص في N يوم". Full read/write access.
- [ ] 0-30 days after expiry: persistent notification, **read-only mode** (can view existing data, cannot create/edit/delete).
- [ ] 31+ days after expiry: full-screen lock with activation/renewal screen.
- [ ] Dates are validated using the clock consistency system (Section F8), not raw wall clock.

### F8: Clock Consistency & Tampering Resistance
**Priority:** P1

**Description:** Detect and mitigate system clock tampering that would extend a trial or expired license.

**Acceptance Criteria:**
- [ ] A `clock-tracker.json` file stores the last-seen wall clock time and an `Instant::now()` monotonic counter.
- [ ] On each startup, if the wall clock has moved backward by > 24 hours, the system enters `Suspicious` mode and uses an estimated time = last_seen_wall + elapsed_monotonic.
- [ ] If the wall clock and monotonic clock disagree by > 24 hours, same `Suspicious` mode.
- [ ] In `Suspicious` mode, a non-blocking notification is shown: "تعذر التحقق من تاريخ النظام."
- [ ] The app **never locks** solely due to clock suspicion. The estimated time is used for licence comparisons.
- [ ] If `clock-tracker.json` is deleted, it is recreated with the current wall clock time (losing history — accepted limitation).

### F9: Lost License Recovery
**Priority:** P1

**Description:** Users who lose their license file can recover it through a web portal and re-activation.

**Acceptance Criteria:**
- [ ] Users can visit `https://license.tuari.app/recover` and enter their email.
- [ ] A one-time recovery link is sent, valid for 1 hour.
- [ ] The link downloads a `license-recovery.lic` file containing the same payload as the original license.
- [ ] Users activate the recovery file through the standard activation flow (F5).
- [ ] The recovery request is rate-limited to 3 requests per email per 24 hours.

### F10: Offline Activation via Response File
**Priority:** P2

**Description:** Users whose Tuari machine has no internet can activate using a response file generated on another device.

**Acceptance Criteria:**
- [ ] The activation screen can display a short "Activation Request Code" (e.g., `ARQ-a1b2c3d4`).
- [ ] The code encodes a nonce and timestamp (no sensitive information).
- [ ] The user can visit `https://license.tuari.app/activate` on any internet-connected device, enter the code, and download an `activation-response.lic` file.
- [ ] The response file is signed with the same Ed25519 key and contains the license payload.
- [ ] The user transfers the file via USB and activates it through the file picker (F5).

### F11: License Display & Status
**Priority:** P1

**Description:** The Settings → Licensing page displays the current license status.

**Acceptance Criteria:**
- [ ] Shows: edition name (in Arabic), licensed customer name, expiry date (if applicable), status (active/warning/expired/grace).
- [ ] Shows a "تفعيل الترخيص" button if no active license is present.
- [ ] Shows an upgrade path CTA: "ترقية إلى Professional" or "ترقية إلى Enterprise" based on current edition.
- [ ] Shows the remaining grace period countdown (if in trial).

### F12: Internal License Generation CLI
**Priority:** P0

**Description:** A command-line tool for generating signed license files (internal use only).

**Acceptance Criteria:**
- [ ] The tool reads an Ed25519 private key file (PEM or raw).
- [ ] It accepts CLI arguments: `--edition`, `--issued-to`, `--email`, `--valid-until`, `--max-users`, `--features`, `--output`.
- [ ] It produces a valid `.lic` file matching the format specified in F1.
- [ ] The tool is documented in the internal wiki.
- [ ] The tool is **not** shipped with the application.

### F13: Key Rotation & Trust Chain
**Priority:** P2

**Description:** The licensing system supports key rotation in case of compromise or scheduled rotation.

**Acceptance Criteria:**
- [ ] The Rust binary can accept one or more "key rotation certificate" files placed in `<app_data>/Tuari/`.
- [ ] A rotation certificate is a JSON file signed by the Root CA key, containing a new Ed25519 public key and an effective date.
- [ ] On startup, the Rust shell reads all `key-rotation-*.json` files, validates the Root CA signature, and adds the new public key to the trusted key list.
- [ ] License files signed with old keys remain valid until their `validUntil` date.
- [ ] If no rotation certificates are present, only the embedded production key is trusted.

## 3. Technical Requirements

### 3.1 New Rust Dependencies

```toml
ed25519-dalek = { version = "2", features = ["pkcs8"] }
base64 = "0.22"
chrono = { version = "0.4", features = ["serde"] }
```

### 3.2 New TypeScript Schema (packages/contracts)

```typescript
// packages/contracts/src/license.ts
export const editionSchema = z.enum(["standard", "professional", "enterprise"]);
export const licenseTypeSchema = z.enum(["perpetual", "subscription", "trial", "grace"]);
export const licensedFeatureSchema = z.enum([
  "lan_server", "multi_user", "encrypted_db", "advanced_reports",
  "multi_site_sync", "audit_export", "external_api", "priority_support",
]);
export const licensePayloadSchema = z.object({
  licenseId: z.string(),
  issuedAt: z.string().datetime(),
  issuedTo: z.string(),
  email: z.string().email(),
  edition: editionSchema,
  features: z.array(licensedFeatureSchema),
  maxUsers: z.number().int().min(0),
  validFrom: z.string().datetime(),
  validUntil: z.string().datetime().optional(),
  licenseType: licenseTypeSchema,
  metadata: z.record(z.unknown()).optional(),
});
```

### 3.6 Environment Variable Changes (Rust ↔ Hono Interface)

Rust passes license information through **structured environment variables**. The raw signed license payload is never exposed to the sidecar. These variables constitute the stable public contract between Rust and Hono (see architecture §15.5).

| Variable | Type | Example | Source in Rust |
|----------|------|---------|----------------|
| `TUARI_LICENSE_EDITION` | string | `"professional"` | `license_manager.edition()` |
| `TUARI_LICENSE_FEATURES` | comma-separated | `"lan_server,multi_user"` | `license_manager.features_csv()` |
| `TUARI_LICENSE_MAX_USERS` | integer string | `"10"` | `license_manager.max_users().to_string()` |
| `TUARI_LICENSE_CUSTOMER` | JSON string | `{"name":"...","email":"..."}` | `license_manager.customer_json()` |
| `TUARI_LICENSE_EXPIRES_AT` | ISO 8601 or empty | `"2027-07-01T00:00:00Z"` or `""` | `license_manager.expires_at()` |
| `TUARI_LICENSE_STATUS` | string | `"active"`, `"trial"`, `"expired"`, `"grace"` | `license_manager.status().as_str()` |

## 4. User Stories

### US-001: Standard User — License Activation
As a user who purchased a license, I want to activate it by selecting the license file so that I can use the full features of my edition.

### US-002: Trial User — Evaluation
As a new user, I want to use the application for 30 days without a license so that I can evaluate it before purchasing.

### US-003: User — Upgrade
As a Standard edition user, I want to upgrade to Professional by activating a new license file so that I can use multi-user and LAN server features.

### US-004: User — License Expiry
As a user with an expiring license, I want to see clear warnings before expiry and know what features I'll lose so that I can plan my renewal.

### US-005: Offline User — Activation
As a user whose Tuari machine has no internet, I want to activate my license by transferring a file from another device so that I can use the full application.

### US-006: User — License Recovery
As a user who lost my license file, I want to recover it through my email so that I can continue using the application.

### US-007: Enterprise Admin — Encrypted Database
As an Enterprise customer, I want to encrypt my database with a key so that sensitive business data is protected at rest.

## 5. Non-Functional Requirements

| NFR | Requirement |
|-----|-------------|
| **NFR-1: Startup Performance** | License validation must complete within 50ms on modern hardware. Ed25519 verification is sub-millisecond; I/O bound by reading a ~2KB file. |
| **NFR-2: Binary Size** | Adding `ed25519-dalek` + `base64` + `chrono` must not increase the Rust binary by more than 500KB (stripped). |
| **NFR-3: Offline Capability** | 100% of licensing operations must work without any network connection. |
| **NFR-4: Arabic Support** | All user-facing license messages must be in Arabic (or properly localized). |
| **NFR-5: Backward Compatibility** | Existing Standard deployments (no license infrastructure) must continue to work. They implicitly enter grace mode. |
