# Payment robustness contracts

The fresh-exact application composition selects `createFreshExactAppDependencies` in `apps/api/src/index.ts`. Its router mounts the financial router and refuses legacy invoice and payment handlers on that startup path. The legacy payment handlers remain available to retained fixture/composition tests; they are not the normal startup implementation.

The exact invoice router exposes payment creation, allocation, deletion and listing through `ExactInvoiceService`. `Money` parses decimal strings into integer units, and `sumMoney` and `applyAllocations` preserve exact decimal arithmetic. The accepted policy is [Exact money contract](../adr/0001-exact-money-contract.md) and [Money foundation](foundation.md). This note adds no rounding rule.

`listPayments` sorts and paginates in common service code for both the in-memory and SQLite exact invoice adapters. Its cursor binds version, collection, sort field and direction, plus a typed sort value and row ID. A malformed cursor, or one created for another collection, field or direction, is ignored and pagination starts at the first page. Supported payment sort values are validated according to their field before applying a cursor.

Exact payment creation accepts a total and allocations in one command. Allocation sums and remaining balances use `Money`; for a total of `0.30` and allocations of `0.10` and `0.20`, the expected unallocated balance is `0.00`. The SQLite invoice and finance repositories share a connection and FIFO lock. The exact finance aggregate transaction composes repository writes on that connection.

`deleteUnallocatedPayment` runs inside the exact finance aggregate command, refuses any payment with allocation history, and deletes only a payment with no allocation rows. The SQLite transaction wrapper uses better-sqlite3 transactions, which create nested savepoints when called within an outer transaction. The command's delete and receipt participate in that wrapper. This describes the exact adapter only.

The retained legacy payment module uses a separate async repository. `deleteIfUnallocated` queues behind the shared async connection lock, then starts `db.transaction.immediate()` and checks allocation history inside that transaction. If a caller opens an outer transaction without holding that same lock, the `await` on the queue does not guarantee that deletion runs before the caller commits or rolls back. Better-sqlite3 can nest its transaction wrapper as a savepoint when execution occurs inside an outer transaction, but that does not make the asynchronous queued method a supported participant in the caller's transaction lifecycle. Treat it as a standalone awaited operation. The legacy repository's `runInTransaction` explicitly detects and joins an already-open transaction; `deleteIfUnallocated` has no such join handling.

Legacy payment creation rejects a duplicate ID with `PaymentDuplicateIdConflictError` (`PAYMENT_ID_CONFLICT`). The repository makes that decision at the insert, before allocation, invoice, or debt writes. It is a conflict, not an update or an idempotent replay. SQLite maps only the `payment.id` primary-key violation; unrelated constraint errors remain database errors.

Legacy `PaymentModule.listPaged` validates the cursor value type against the effective sort field, which defaults to `createdAt`. `totalAmount` needs a finite number; the date fields retain the legacy string-or-null cursor shape. The cursor still stores only `sortValue` and `id`, so a string cursor reused between date fields cannot be identified as a field mismatch. This fix does not change that wire format.

Legacy amounts remain JavaScript numbers under the shared positive bounded schema. The module does not quantize them, and it compares the allocation sum with strict number equality. For example, JavaScript evaluates `0.1 + 0.2` as a value different from `0.3`, so that allocation sum can be rejected. This records the legacy behavior; it adds no rounding rule. The exact-money path continues to use `Money` as described above.
