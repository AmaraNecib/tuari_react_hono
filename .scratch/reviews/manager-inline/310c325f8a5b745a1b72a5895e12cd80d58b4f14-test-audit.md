## Answers to the gate questions

- **Do the tests assert the REAL id returned by the mutation, and would a
  fabricated id fail them?** Yes. `project-create-page.test.tsx` submits and
  asserts `managerId: "emp-new-1"` (the id the mocked mutation returns);
  `warehouse-create-page.test.tsx` asserts `managerId: "emp-whm-9"`; and
  `workspace-mutations.test.ts` pins `output.employees` equal to the RPC rows.
  Reintroducing `{ id: "new" }` fails the page suites; dropping the `employees`
  field fails the hook suite.
- **Is "other fields survive" meaningful?** Yes — form state lives in the page,
  so a page reset/remount on create would clear `name`/`location`/`notes`, and
  the assertions plus the submitted payload would catch it. It would not catch a
  reset scoped inside `ProjectFormFields` (stateless), which is not a real path.
- **Is the removed debt-worker create asserted as absent, not merely untested?**
  Yes — `debt-create-page.test.tsx` opens the listbox and asserts
  `queryByRole("option", { name: /إضافة موظف/ })` is `null` while also asserting
  the existing worker option is present, so an empty listbox cannot false-pass.

## Remaining, not fixed

- Edit-page inline *create* (as opposed to the select/clear path) has no direct
  test; it shares `ProjectFormFields`/`WarehouseFormFields` and the hook with
  the covered create pages.
- Empty-required-field validation in the create dialog is exercised only
  implicitly (the in-flight test fills the field).
- An existing `getByText(...).toBeTruthy()` pattern is redundant (getByText
  already throws) but is not a false pass.
