  silently alters user-chosen passphrase secrets; SQLCipher compares byte-for-byte;
  if the initial DB key was set via an untrimmed path, trim could lock the user out.
- **F2 (5)** rationale inconsistency: doc refuses to trim app passwords because
  whitespace is legitimate in secrets, yet trims DB keys.
- **F3 (3)** `{ success: false, error: "" }` passes — failure member has no `min(1)`.

- **F5 (2)** inferred output type narrowing is semver-visible / breaking for external
  consumers of the now-public schema.
- **F6 (3)** design-doc assumptions unverified: recovery-key generator alphabet and
  the stored-DB-key setup path are never shown to be whitespace-free.
- **F7 (2)** `.scratch/implementation/221-design.md` committed into the branch.
- **F8 (2)** `router.test.ts` `expect(consumeKey).toHaveBeenCalledTimes(2)` is
  brittle (coupled to the exact call count).

## Defender defenses (confidence 1–10)

- **D1 (9)** trim at the contract seam is the correct home for normalization — the
  deletion test holds; every caller (handler hash comparison, PRAGMA verification)
  gets it for free.
- **D2 (9)** strict discriminated union is load-bearing: a non-strict union would
  strip `{ success: true, error }` instead of rejecting it; the two invalid combos
  throw, the two valid pairs parse; consumers get real type narrowing.
- **D3 (9)** leaving app passwords untrimmed matches repo convention (`auth.ts`
  keeps passwords untrimmed while copyable/name fields are trimmed).
- **D4 (9)** zod semantics verified empirically on the repo's zod ^4.0.5.
- **D5 (8)** tests pin behavior (worked-example literals, boundary values on the
  TRIMMED value, exact invalid combos).
- **D6 (9)** no live path broken: handler emits exactly the two valid shapes; the
  existing wire failure test still resolves through the union.

## Synthesis (decisions)

| Finding | In scope | Action |
|---|---|---|
| F1 (8) | Yes | **Dismissed — disproven by codebase evidence.** The DB key is machine-generated, never user-typed: `apps/desktop/src-tauri/src/lib.rs` `generate_secret(32)` produces a 64-char lowercase-hex token, and `load_or_create_secret` already `.trim()`s the stored value on load. Hex tokens contain no whitespace, so trim is a no-op for legitimate keys. Trim is actually *load-bearing*: without it, a rekey to `"  key  "` would store a key the Rust load path (which trims) could not reproduce on restart → DB fails to decrypt. Evidence recorded in the design doc. |
