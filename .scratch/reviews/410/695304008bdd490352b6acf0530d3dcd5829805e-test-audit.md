## 3. Is the new ordering assertion a real guard or decorative?

**Real.** `tests/sqlcipher-encryption-proof.test.mjs:162-170`:

```js
assert.ok(WRITE_ROW_PROBE_SOURCE.indexOf('db.pragma("key = ') < WRITE_ROW_PROBE_SOURCE.indexOf("INSERT INTO proof"), ...)
assert.ok(READ_ROWS_PROBE_SOURCE.indexOf('db.pragma("key = ')  < READ_ROWS_PROBE_SOURCE.indexOf("process.env.TUARI_PROOF_SQL"), ...)
```

- The sources are line arrays joined with `\n` (`sqlcipher-encryption-proof.mjs:254-282`); the key line is `'db.pragma("key = \'" + key + "\'");'`, which contains the literal substring `db.pragma("key = `. `indexOf` returns the key line's offset (0 in both), and `INSERT INTO proof` / `process.env.TUARI_PROOF_SQL` appear later. Assertion holds on the current source.
- **Move the key pragma after the write/query and `indexOf` key > `indexOf` anchor → `assert.ok(false)` → red.** So it closes the exact hole round-2's LOW-4 named (a reorder stayed green under presence-only checks).
- Deletion is still caught, by the `assert.match` above it first: if the pragma were removed, `indexOf` returns `-1` and the bare ordering comparison alone would spuriously pass — but the presence assert throws before that line runs, so a deletion is never green. Combined, the guard is sound for both mutations.

Verdict: not decorative. One residual (unchanged from round 2, LOW): it is a *textual* guard — it pins source order, not runtime order; the runner's step 3/4 remain the behavioural proof. That limitation is stated in the test comment ("Structural, not behavioural").
