## Post-evidence delta (c355e62 — review comment round, pre-delivery RPC failure)

Review comment on `recovery-key-hooks.ts` (lines 148-152): when the desktop
bridge throws BEFORE delivering the rekey RPC, the database has not been
rekeyed, but the catch block called `complete_db_key_rotation` and cleared
the only old-key rollback slot — the secret store then held the new key
while the database still required the old one, so the next startup could
not decrypt the database. **Valid finding, fixed.**

- **`apps/web/src/features/app-shell/recovery-key-hooks.ts`**: the catch
  block now classifies the thrown error via `rpcFailureProvesNoRekey()`:
  - Request NEVER DELIVERED (transport/bridge failure — no ORPC code/status)
    or server rejected with a client error (status 4xx, excluding the
    timeout-ish 408/499): the database was DEFINITELY not re-encrypted →
    `restore_db_key` (roll the rotation back). The previous blanket
    "keep the new key + complete" behavior is gone for these cases.
  - 5xx / timeout-ish server error (handler may have rekeyed before
    failing): keep the new key AND the rollback slot — neither restore nor
    complete — matching the server-side `ambiguous: true` "verification
    pending" semantics (strictly safer than the old complete-on-any-error,
    which dropped the only way back when the rekey had NOT happened).
  - The classifier uses the ORPCError contract (server errors always carry
    string `code` + numeric `status`); their absence means no server
    response. The desktop bridge talks to a LOCAL loopback API, so a
    delivered-but-response-lost failure is not realistic — the dominant
    transport failure is connection-refused (API not running), provably
    pre-delivery.
- **Tests** (`recovery-key-hooks.test.tsx`): rewritten throw-path tests —
  plain transport error → restore (no complete); 401 ORPC error → restore
  (handler never ran); 500 ORPC error → keep new key + rollback slot (no
  restore, no complete); the pre-delivery restore-failure is swallowed so
  the original error still surfaces.

## Post-evidence delta (e7d2920 — Greptile P1 round, PR #352: response-body read failures)

Greptile (4/5, do-not-merge) on PR #352: `recovery-key-hooks.ts` lines
107-108 — the catch path treated ANY thrown error lacking ORPC metadata as
proof the database was not re-encrypted and restored the old key. A
post-delivery failure (the Rust bridge receives HTTP headers, then fails
reading the response body) carries no ORPC metadata either, so the
classifier restored the old key over a database the API had already
rekeyed — the next startup failed to decrypt.

**Protocol fix (smallest explicit marker at the bridge seam):** the Rust
`desktop_api_request` command now returns a structured error
`{ message, desktopBridge: { kind: "desktop-api-bridge", phase } }` with
`phase` in `pre-delivery | response-body-read | unknown`:

- `pre-delivery` — failure before any HTTP bytes are sent (request
  construction/validation, window/path gating, auth-session resolution,
  reqwest connect error). Provably no rekey.
- `response-body-read` — response headers received but the body read
  failed. The API may have rekeyed; outcome unknown.
- `unknown` — any other send failure (non-connect reqwest error).

The web bridge preserves the native phase through
`invokeDesktopBridgeCommand` (falling back to `unknown` for unmarked
rejections) and marks request-construction failures `pre-delivery` (the
invoke never ran). The rekey hook restores the old key ONLY on an
explicit `pre-delivery` marker or an ORPC client error (4xx excluding
408/499); every other thrown error keeps the new key AND the rollback
slot (pending), so a rekeyed database is never orphaned.
