## Synthesis

**Fixed, with a test**

1. `roundMoney` (`apps/api/src/modules/company/report.helpers.ts`). The multiply
   by 100 is exact only below `MAX_SAFE_INTEGER / 100`; above it the helper now
   returns the value unchanged. Verified: `roundMoney(MAX - 1)` is `MAX - 1`
   again, and `roundMoney(MAX)` is `MAX`. Pinned by
   `apps/api/src/modules/company/report.helpers.test.ts` and the near-bound
   project-total test in `asset-charge.service.test.ts`. The web copy in
   `transfer-item-dialog.tsx` got the same guard.
2. Correction editor (`apps/web/src/features/inventory/asset-charge-history.tsx`).
   `saveEdit` now uses `parseChargeAmountInput`; only `{ kind: "amount" }` is
   accepted, so blank and non-numeric drafts show an inline error and write
   nothing. Pinned by two tests in `asset-charge-history.test.tsx`.
3. Client amount parser (`apps/web/src/features/inventory/transfer-item-dialog.tsx`).
   `parseChargeAmountInput` now returns `invalid` for `> MAX_MONEY_DZD`, so a
   large percentage cannot produce a submittable over-bound amount. Pinned by
   `transfer-item-dialog.test.tsx`.

**Dismissed, with evidence**

4. Finding 2 is disproved: `InventoryService.transferAsset` refuses a transfer
   to the unit's current location with `InventoryError("BUSINESS_RULE",
   "الأصل موجود بالفعل في هذا الموقع.")` before the transaction opens
   (`apps/api/src/modules/inventory/inventory.service.ts:604-606`). The critic
   did not see the guard. No duplicate charge can be booked this way.
5. Finding 7 is unreachable: `updateCharge` and `voidCharge` are synchronous,
   better-sqlite3 is synchronous, and there is no `await` between
   `requireLiveCharge` and `withTransaction`, so no other call can interleave.
   It becomes real only if the seam turns async or multi-process.

**Out of scope, reported to the parent**

6. Finding 5. The invoice consumable `unitPriceDzd`, `grossTotalDzd` and
   `paidAmountDzd` are unbounded, but those schemas predate #413, their output
   contract is deliberately unbounded, and no charge path reads them. This is a
   pre-existing money-rule gap, not the two-ceiling bug. Proposed follow-up: give
   the invoice money fields the same `MAX_MONEY_DZD` rule and an aggregate guard
   on `grossTotalDzd`. The parent decides whether to fix it here or in a new
   issue.

**Accepted minors, documented**

7. Finding 6: RESTRICT would also block deleting a project whose only charges are
   VOIDED. No project-delete path exists, and the policy is already recorded in
   the round-1 design note. If a delete feature lands it must decide the voided
   case explicitly.
8. Finding 8: the in-memory adapter does not persist `voidedBy` (the record type
   has no such field, and the contract does not expose it), and the void button
   records `reason: null` unless the row was opened for edit. Both are audit
   polish, not wrong numbers.
9. Finding 9: `getLastChargeAmount` means "most recently recorded live charge",
   which is what "last charge for the unit" means here. `occurredAt` is a
   back-dating field on the movement, so insertion order is the honest key.
10. Findings 10-12: the web keeps its own `roundMoney` because it cannot import
    `apps/api`; percent -150 correctly clamps the amount to 0; the default query
    firing on an open asset dialog is one wasted request.
