## Spec

Issue #412 and `.scratch/implementation/412-design.md` read directly.

Requirements present:

- Periods offered: DAILY and MONTHLY only; WEEKLY kept in the enum and rendered
  for legacy employees (`employee-edit-page.tsx` pushes it only for the stored
  value). Verified in the diff.
- Monthly day rate `salary / 30` via `computeProposedSalaryAmount`, shared by the
  API and both web forms; amount stays directly editable.
- Per-project split, hand-typed, prefilled from assignment windows inside the
  period; open-ended windows run to period end; no assignment → unallocated.
- Reconciliation as an upper bound (`sum(split days) <= paid days`), remainder
  stays unallocated — matches "A remainder may stay unallocated rather than
  being forced onto a project".
- Migration: `days INTEGER NOT NULL DEFAULT 30` in the fresh CREATE plus the
  additive ALTER; split table with CASCADE/RESTRICT FKs and both indexes; legacy
  amounts untouched (pinned by `schema-migrations.test.ts`).

Notes (not defects):

- The DAILY default is `1`, not the issue's monthly-scoped "default 30". This is
  a recorded parent decision from round 2: defaulting a daily worker to 30 days
  proposes 30× the day's wage. The dialog and the quick form share
  `defaultSalaryPaymentDays`.
- Normalizing covered calendar days to the payment's day count (February → 30,
  March → 30) is a recorded parent decision, not scope creep.

Spec fix at `99c3af38`: the quick form's zero-amount guard now matches the
service and the dialog; day counts past the safe-integer range are rejected at
the service boundary and in the digits-only parser.
