## domain-modeling

- The change adds no new money vocabulary: it reuses the two existing shapes —
  `nonNegativePaymentAmountSchema` (write/aggregate bound) and
  `storedMoneyDzdSchema` (permissive persisted read). The "one money rule" is
  now stated once and imported, not re-typed.
- Fix applied in this pass: `inventoryEntrySchema.unitPriceDzd/totalPriceDzd`
  were hand-written `z.number().nonnegative()`; they are now the named
  `storedMoneyDzdSchema`, so the read-shape rule has one name.
- The new aggregate rule ("a batch of individually legal lines must still sum
  within `MAX_MONEY_DZD`") is stated once in `accumulateGrossTotal` and called
  from both accumulation sites.

## codebase-design

- `accumulateGrossTotal(current, line)` is a deep, small helper: it returns the
  next total or throws. Deletion test: remove it and the overflow is once again
  silently stored — it earns its place.
- Seam check: the wire gate (`nonNegativePaymentAmountSchema`) and the module
  seam (`normalizeMoneyWithinBound`) parse the SAME schema, so a direct caller
  cannot store what the contract rejects (#289 pattern) — a real seam, not a
  hypothetical one.
- No shallow wrapper was added; `normalizeMoneyWithinBound` gained a message
  parameter instead of a second near-identical function.

## improve-codebase-architecture

Friction this diff created or exposed:

1. **Stored-vs-aggregate output asymmetry (open, parent decision).** The group
   totals are now strict (`max`) while the line money they sum stays permissive
   (`storedMoneyDzdSchema`). A legacy above-bound invoice reads its entries but
   fails on its group. The brief explicitly asked for the output bound, so it is
   implemented and documented; the alternative (permissive group read + rely on
   the write gate) is surfaced to the parent in the handoff.
2. **Third copy of a money-sum guard.** `accumulateGrossTotal` joins
   `AssetChargeService.sumLiveCharges` and `project-cost.service.sumMoney`. Each
   refuses with its own domain error and message, so a shared helper is not
   obviously better; unifying them is a cross-module refactor, filed as a
   follow-up candidate rather than folded into this feature PR.
3. **PERCENT path still calls unbounded `normalizeMoney`.** Transitively safe
   (`percent ≤ 100` ⇒ result ≤ grossTotal ≤ MAX, and overpayment is refused), so
   it is left as-is; pinned by reasoning, not a new test.
4. **`inventoryInvoiceGroupRecordPaymentInputSchema.amountDzd` and the outbound
   money inputs remain unbounded** (pre-existing, safe in practice). Noted in
   the design doc as a separate cleanup, not this issue.

Cheap cleanups done in this diff: entry money single-sourced to
`storedMoneyDzdSchema`; dead default parameter removed.
