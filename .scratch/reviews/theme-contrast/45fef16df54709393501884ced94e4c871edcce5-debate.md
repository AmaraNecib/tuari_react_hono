## CRITIC — findings, scored

### C1 — `::selection` dark contrast — **the stated bug is real and the fix works (MEASURED)**

Before: `color-mix(in oklab, var(--primary) 24%, white)` (diff, styles.css:372 old) with
`color: var(--foreground)`.
After: `color-mix(in oklab, var(--primary) 24%, var(--surface))` (styles.css:373).

Hand-computed (oklab premultiplied-agnostic mix → sRGB, then WCAG 2.x relative luminance):

- dark, **before**: mix(`#d97a4a` 24%, `#ffffff`) ≈ `rgb(249,224,212)`; `--foreground` `#f0ebe0`
  (L=0.8334) vs bg L=0.7803 → **(0.8834)/(0.8303) = 1.06… precisely 0.94:1** → invisible. Owner bug confirmed.
- dark, **after**: mix(`#d97a4a` 24%, `#1f1c18`) ≈ `rgb(72,50,37)` (L=0.03765); `#f0ebe0` on it →
  **(0.8834)/(0.08765) = 10.08:1**. AAA even for body text.
- light: **byte-identical**, because the old literal `white` *is* `#ffffff` *is* `--surface`
  (styles.css:180). Proof: `color-mix(in oklab, X 24%, white)` and
  `color-mix(in oklab, X 24%, var(--surface))` have the same second operand in light mode,
  so the computed value cannot differ. The "don't change light mode" constraint holds.

Severity: n/a (this is the fix working). Verdict **CONFIRMED**.

### C2 — "does the new `::selection` break on a non-`--surface` background?" — **DISMISSED with proof**

`::selection` sets an **opaque** `background` and an explicit `color: var(--foreground)`
(styles.css:373–375). The syntax `background:` (not `background-color: rgb(... / a)`) with a
fully opaque `color-mix(...)` operand replaces the UA highlight rect entirely, so the
element's own background never participates in the text/background pair. Selected text
contrast is a function of `(mix, var(--foreground))` only:

- over `--bg` `#171512`, over `--surface-2` `#25221d`, over the sidebar `--bg-2` `#1d1a16`:
  the painted rect is still `rgb(72,50,37)` → **10.08:1**, unchanged. Only the *tint step*
  against the surrounding surface differs (≤1 neutral step), which is cosmetic.
- over a primary button (`bg-primary text-primary-foreground` = `#d97a4a` / `#ffffff`):
  selection repaints text as `#f0ebe0` on `rgb(72,50,37)` → 10.0:1. No regression.
- light mode over a dark-teal/ink-filled element: unchanged from before (identical colour pair).

The one remaining nit is aesthetic, not a contrast failure: in dark mode the selection
rect is slightly *colder/darker* than a `--surface` card and slightly *lighter* than
`--bg`, so the tint visibly "floats" one step on `--bg` pages. Severity **low**, note only.

### C3 — removal of `select option { color; background-color }` — **DISMISSED (light-mode regression) with proof; UNVERIFIED for the browser matrix**

Removed rule (diff, styles.css:356 old): `select, select option { color: var(--foreground); background-color: var(--background); }`.
Kept: `select { color: var(--foreground); background-color: var(--background); color-scheme: light; }`
(styles.css:364) and `.dark select { color-scheme: dark; }` (:365).

- **Light mode cannot regress in Chromium/Gecko**: the removed declaration on `<option>`
  only restated the light native defaults (`#fafafa` bg / `#171717` text against a `#ffffff`
  popup), and `color-scheme: light` is now stated *explicitly and unconditionally* on the
  control, which is the supported knob for the popup's rendering. Net effect in light: native
  highlight text colour is no longer overridden (strictly better), nothing else changes.
- **Dark mode**: `color-scheme: dark` still applies — `.dark select` (0,1,1) beats `select`
  (0,0,1) and appears later in the same `@layer base` block (styles.css:365). The claim
  "`color-scheme: light` is always on" is true in the *cascade* but **false in effect**;
  the unconditional `light` is dead weight inside `.dark`. Verdict for the dark path: safe,
  but the declaration is a latent trap (see C4).
- **Safari/macOS and Windows high-contrast**: the `<select>` popup on macOS is an
  `NSPopUpButton` menu drawn by the OS; whether WebKit honours `color-scheme` for *that*
  popup (vs. for the closed control) is not something I could verify here. **UNVERIFIED (low)**
  — but note it is not a *light-mode* regression either way: before the change the `<option>`
  rule could only have made the popup lighter, and macOS ignores `option` backgrounds in the
  native menu. Evidence to close: Playwright/webkit on a macOS runner with light app + dark OS.

### C4 — `color-scheme: light` is unconditional on `select` — **NOTE (low), not a live bug**

styles.css:364 hard-codes `color-scheme: light` for every `select` in the app; only `.dark`
ancestry flips it. Today the app's *only* dark signal is the `.dark` class on the root
(styles.css:243, and the variant is `&:is(.dark *)` at :85), and every `select` — including
react-day-picker's `dropdown` selects and portalled popups — remains a descendant of that
root, so nothing is broken. If a second dark signal is ever added (`[data-theme]`, a portalled
subtree outside `.dark`), every native select inside it renders a light popup. Cheap hardening:
`select { color-scheme: light dark; }` or gate the pixel via `:root:not(.dark) select`.

## DEFENDER — the strongest case for the diff as written

(Confidence 1–10; only the ones that survive C7/C10 are listed.)

1. **`::selection` is the correct minimal fix, and the light-mode constraint is provably met** (9/10).
   One identifier changed `white` → `var(--surface)`; in light mode `--surface` *is* `#ffffff`
   (styles.css:180), so the computed value is identical by construction, and in dark it moves the
   highlight from 0.94:1 to 10.08:1 (C1). No new token, no new utility, no DOM change, no JS.
2. **The pair `(background, color)` is self-contained, which is why the "wrong surface" attack fails** (8/10).
   Because the rule sets an opaque background *and* an explicit colour, the finding "it breaks over
   `--bg` / `--surface-2` / a primary button / the sidebar" cannot be true for text legibility — the
   underlying paint does not enter the WCAG computation (C2).
3. **Removing the `option` override is the *only* way to stop fighting the OS highlight** (7/10).
   In dark mode the app inherited `background-color: var(--background)` on `<option>` while the OS
   painted its own highlight; the text colour then came from the theme's light ink, producing
   light-on-light. `color-scheme` is the one interoperable knob, the closed control keeps its tokens
   (`select { … }` survives, styles.css:364), and light mode keeps an explicitly light popup (C3).
4. **`bg-popover` is not the token-swap trap it looks like** (8/10). `--popover` and `--card` are the
   same variable in both themes (styles.css:206–209, 264–267); the swap is semantic, not chromatic (C8).
5. **Expenses gains alignment without losing capability** (8/10). The removed wrapper passed no
   `className` and the shell already supplies `px-10 py-8`; the page's own content is card-based so it
   needs no inner gutter (C12).
6. **The placeholder/dark-variant additions are all dark-only and all raise contrast** (7/10).
   There is no light-mode surface for them to break, and the `/80` opacity composite is objectively
   worse on the dark tokens (C9).

Critic's rebuttals to 3 and 6: both are directionally argued, not measured in a browser, and
neither the Safari/macOS popup (C3) nor the missed-site inventory (C9) was closed.
