## P3 — item 2, highlighted/selected option state → **CONFIRMED correct**, one nuance

`select.tsx:161`: `focus:bg-accent focus:text-accent-foreground` → `data-[highlighted]:bg-accent
data-[highlighted]:text-accent-foreground dark:data-[highlighted]:text-foreground data-[selected]:font-medium`.
- Register: `dark:data-[highlighted]:text-foreground` wins over `data-[highlighted]:text-accent-foreground`
  by specificity — it carries an extra `:is(.dark *)` class, so it is 0,3,0 vs 0,2,0. Robust regardless of
  declaration order.
- Light row text stays `--ink-2` = `rgb(64,64,64)` @ **8.3:1** on `#f0e0d3` — matches the doc's
  "measured `rgb(64,64,64)` (unchanged)" exactly (corroborated independently).
- **Nuance (low, CONFIRMED by measurement):** in dark the highlighted row's text is now *the same*
  `#f0ebe0` as every non-highlighted row, so the sole highlight cue is the surface change
  `#2e2418` vs `#1f1c18` = **1.12:1**. That is below WCAG 1.4.11's 3:1 for state indicators — but it is
  also within one step of the app's own light-mode highlight (`#f0e0d3` on `#ffffff` = **1.17:1**),
  i.e. consistent with the established design language, and *better* than the pre-fix state where
  `:focus` frequently painted nothing. Not a blocker; if increased cue strength is wanted, use
  `dark:data-[highlighted]:bg-surface-2` (`#25221d`) or a ring, not a text-colour change.
- **Doc accuracy (low, CONFIRMED):** the design doc's "measured 9:1 vs the previous 5.9:1" does not
  reproduce: `--ink` on `#2e2418` = **12.9:1** and `--ink-2` on `#2e2418` = **8.6:1**. Both exceed AA, so
