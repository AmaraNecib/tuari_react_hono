# Share the approval identity lock with account updates

Bounded follow-up to account-cache-f12eae51-review-01.md P1: `home-view.tsx:304` lets legacy-mode Settings save account changes without the approval fence. An unresolved approval can still be followed by an account rename in that route.

Move the guard into `useUpdateAccountSettingsMutation`, which supplies both exact and legacy Settings. Remove the redundant exact-only callback wrapper. Account identity belongs to the user, not one workspace, so the shared mutation enumerates existing v1 intent keys for that authenticated user. It blocks if any matching value exists, including malformed records. It does not interpret, rewrite or clear that evidence. Another user's keys and unrelated localStorage records do not block. Missing session, storage failure and unavailable coordination fail before identity changes.

Integrate the separately committed cross-tab executor ownership correction, then use one Web Lock name for this user's approvals and account changes. The executor holds that lock across durable reload, save, send and clear/uncertain persistence. Account changes hold the same lock across durable record enumeration and both profile/password requests. This closes the check-to-save race: an approval cannot start mid-rename, and a rename queued behind a lost approval response sees its persisted uncertain record. Serializing a user's approvals across workspaces is intentional because their audit identity is shared. Lock names are coordination only; the v1 storage key/envelope and persisted server receipt/fingerprint remain unchanged. No dependency, schema, contract, policy or CI changes.

The shared mutation tests run the actual callback used by legacy Settings and assert refusal before profile/password APIs. Coordination regressions use the real store/executor and account helper over one keyed lock queue; they test both orderings with transport failures. Browser Web Locks are absent in jsdom, so caller tests now provide an asynchronous keyed queue rather than bypass the lock. The original 8 caller failures from missing Web Locks are preserved in account-identity-lock-01.log. Updated caller, recovery, editor, mutation and coordination proof passes 58 tests in account-identity-lock-02.log; final changes require refreshing affected proof before commit. Web types and affected lint passed before the last cleanup and must be refreshed.

Verification remains focused-local / CI-final-pending. This is a same-origin UI coordination boundary, not server authorization against arbitrary external clients or old app versions. Final hosted review and CI are still required. Existing cache-refresh findings remain resolved under the prior review; service-coverage and E2E alignment are separate work.
