## Domain decisions

A salary reference is optional, period-tagged context, not earned wage, a payroll liability, a payment ceiling or permission to prorate. DAILY accepts up to four decimal places; MONTHLY and legacy WEEKLY references use two. Changing the period does not reinterpret or convert the amount. Missing, zero and nonzero references remain distinct. An employee can receive an explicit earning approval without a reference. No automatic salary proration or ceiling is introduced.

An approval is an immutable earned-wage record, separate from legacy cash-payment history. It stores the exact approved total, explicit unallocated amount, period, optional reference snapshot and ordered project segments. Segment IDs are stable and unique within an approval; repeated project IDs are valid, so A/B/A remains three distinct rows in original order. Each segment has its own explicitly approved amount and days. No row edit silently changes another row or the total; no approval silently reallocates amounts. Allocated segments plus unallocated amount must equal the approved total.

The canonical UTC period is validated before the request fingerprint is computed or persistence begins. A retry with an equivalent offset representation therefore maps to the same earning. The request fingerprint includes the approved payload, including days, so omitted or changed segment days cannot reuse an earlier request identity. Retries reuse the same request ID and frozen payload after an uncertain response. Only a response that establishes no write permits correction of a first attempt. In the web UI, another tab removing stored pending state does not replace the already-frozen in-memory request; after a successful local approval, an intentional new approval starts a new request.

Money enters and leaves the feature as exact decimal strings. The accepted #522 exact-money types and integer persistence handle new earning amounts; they never cross JavaScript `Number`. Existing `Number` uses for bounded day counts or presentation-only ratios do not authorize numeric money conversion.

## Inventory writer compatibility correction

The bounded #543 inventory correction finalizes invoice-group amounts without converting all inventory money storage. Public inputs remain numeric. Purchase quantity accepts the established six-decimal quantum and now enforces that precision at purchase input; quantity validation semantics are not unchanged. Native numeric exponent forms are expanded to canonical decimal operands without rounding. The raw product is retained for legacy line-value storage and reporting.

Entered unit prices must fit the accepted `UnitPrice` range before any transaction writes. The invoice header separately parses canonical base-10 forms of the original accepted numeric operands, multiplies and sums them exactly, then rounds the complete document sum once to two places. It does not calculate the header from rounded line values or binary Number products. Asset F amounts enter that same exact sum. For example, raw products `0.1234` and `0.012` finalize together to `0.14`; two raw `0.375` products finalize to `0.75`, not `0.76`.

The finalized gross is the source for paid and remaining amounts and the debt ledger. Percent-based initial payments also calculate from that finalized gross with exact decimal percentage arithmetic. Before transaction writes, the writer checks the DZD bound and verifies that each finalized F amount survives conversion to legacy REAL and back to the same cents. Existing whole amounts through `Number.MAX_SAFE_INTEGER` remain supported. This starts at the numeric operand that reaches the server; it cannot recover decimal intent already lost in JSON Number transport. Inventory line products remain legacy REAL intermediates. This correction does not convert other inventory financial paths, replace numeric legacy transport, change REAL storage or add a migration.

The project-cost report continues to finalize each valued material movement independently. Existing stock-charge rounding and REAL storage remain unchanged. The project-cost SQLite adapter reads affected legacy REAL values through SQLite's native number decoder before strict `Money` or `UnitPrice` parsing: asset-charge amounts, consumable unit prices and parked asset purchase prices. It does not cast those REAL values to text, which can emit exponent notation for large whole values. Exact approved earnings remain text/int64; expense already uses the native decoder and is untouched.

The source module interface remains the existing numeric inventory RPC and read-only project-cost repository. No adapter seam moved. A private exact accumulator keeps invoice arithmetic local to `InventoryService`; it accepts canonical legacy operands, not an intermediate product. Contract and service validators share input scale rules. Focused authenticated tests cover once-rounded mixed products, half-cent lines, payment/debt consistency, no-debt mode, overflow rollback, high whole amounts, large REAL readback and unchanged stock-charge results.
