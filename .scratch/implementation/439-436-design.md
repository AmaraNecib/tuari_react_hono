## Context

The backup engine merged in #434/#430 already: `VACUUM INTO` snapshots on
startup into `<root>/<YYYY-MM-DD>/`, retention 14/8/6 (`BACKUP_RETENTION`), a
`snapshot.json` marker, and an auth-gated `backupStatus` RPC
(`{ lastSuccessAt, lastBackupPath, lastFailure }`). Nothing consumes the RPC and
the desktop cannot move the root.

## #439 — status surface

### Where

The Settings → **System** tab already holds system-level rows (updates, reset,
database export placeholders). A new self-contained `BackupSettings` component
is dropped there; no new page, no nav entry.

### Contract change (extend, as the issue allows)

`backupStatus` currently cannot answer "where is the folder" when no backup has
ever run (`lastBackupPath` is null) and cannot state the retention policy. Both
are needed by the screen. Extend `backupStatusSchema`:

```ts
backupStatusSchema = {
  lastSuccessAt: timestamp | null,
  lastBackupPath: string | null,
  lastFailure: { at: timestamp, reason: string } | null,
  backupsRootPath: string,                       // NEW: always the configured root
  retention: { daily: int, weekly: int, monthly: int }, // NEW: BACKUP_RETENTION
}
```

The service (`getStatus`) returns both; the policy constant stays the single
source of truth (`backup.service` reads its injected `policy`).

### UI states (each renders distinctly)

- **never run**: `lastSuccessAt === null && lastFailure === null` → "no backup
  yet" + an empty-state that explains the daily DB-only copy on the same disk
  and does **not** claim protection against disk failure.
- **succeeded**: `lastSuccessAt !== null` → last success time + path.
- **failed**: `lastFailure !== null` → loud failure reason + time. A later
  success clears `lastFailure` server-side, so "failed" means the last attempt
  failed.

Text is Arabic through i18n; layout uses semantic tokens only. Timestamps go
through the existing Algeria formatting helper.

## #436 — backup-folder setting

### Honest alternative chosen

A native folder picker exists only in the desktop shell; the web/dev build has
no such thing. So the field is a **path input with validation**, plus a "Choose
folder…" button that opens the existing Tauri dialog plugin
(`@tauri-apps/plugin-dialog`, the same pattern `update-commands.ts` uses) when
running in the desktop runtime. The web build keeps the path field.

### Persistence + forwarding (no Rust change needed)

The desktop shell already spawns the sidecar with `TUARI_CONFIG_FILE=<tuari>/
config.json`, and the API reads that file (`loadConfigFile` → `mergeConfigIntoEnv`
→ `createAppConfig`). Add a `backups_root` field to the config-file schema and
map it to `APP_BACKUPS_ROOT`. That is the forwarding path the issue asks for:
the shell does not forward the env var, but the config file it points at does.

New RPCs:

```ts
setBackupsRoot: input { path: string } -> 
  { success: true, path: string, persisted: boolean } |
  { success: false, error: string }
```

Flow: validate the path (`backup.settings.ts`, fs-backed) → persist to the
config file (`BackupFolderPersister`, atomic read-modify-write) → on success
call `backupService.setBackupsRoot(path)` so the running process's status/next
run use it. A failed validation or persistence returns the honest error and
leaves the old root alone.

If no config file is configured (bare `pnpm dev:api`), persistence is
unavailable; the result is `success: true, persisted: false` and the UI states
that the choice applies to this session only — the honest web-build limitation.

### Degrade, never block

An invalid or unwritable configured root already degrades in the service: the
constructor seeds a recorded failure from `seedStatusFromDisk`, and a run
failure is recorded non-fatally. The new validator only guards the *setting*
action; it must not make startup fail. A test pins the service behaviour when
the root is a file / unreadable.

### Validation messages name the problem

- empty → "backup folder path is required"
- a file at the path → "the path is a file, not a folder: <path>"
- mkdir/access failure → "cannot use this folder: <reason>"

## Modules and seams

| Module | Role |
| --- | --- |
| `modules/backup/backup.settings.ts` | pure-ish fs validator for a chosen root |
| `infrastructure/config/config-file-writer.ts` | atomic read-modify-write of config.json (extracted from the key persister) |
| `infrastructure/config/backup-folder-persister.ts` | `BackupFolderPersister` port over the writer |
| `rpc/handlers/backup.ts` | validate → persist → apply, auth-gated mutation |
| `web/.../backup-hooks.ts` | query + mutation + desktop picker |
| `web/.../backup-settings.tsx` | the status/setting surface |

The service owns the mutable root; `setBackupsRoot` re-seeds the status from the
new root so the screen never describes the old folder.

## Risks / decisions

- Preserving every unrelated config field while writing `backups_root`; the
  shared writer rejects a merged document the loader would not accept.
- Changing `getStatus()` shape breaks existing strict `toEqual` service tests;
  they are updated, not weakened.
- The picker returns a directory path from the Tauri dialog; in a non-desktop
  runtime it returns `null` and the path field is used.

## Tests

- API: config loader maps `backups_root` → `APP_BACKUPS_ROOT`; folder
  persister preserves fields / atomic failure; validator rejects file/empty/
  unwritable with a naming message; service status includes root+retention and
  `setBackupsRoot` makes the next run write to the new folder; unreadable/file
  root degrades to a recorded failure.
- Router: `backupStatus` carries the new fields; `setBackupsRoot` requires a
  session and returns the validation error for a bad path.
- Web: `BackupSettings` renders never-run / succeeded / failed states; saving a
  valid path calls the mutation and shows success; an invalid path renders the
  server error message.
